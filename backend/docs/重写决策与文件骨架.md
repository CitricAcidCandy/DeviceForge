# DeviceForge 重写决策

## 命名与目标
DeviceForge，中文设备工坊。名称覆盖设备调试、应用分析、自动化和开发者扩展。独立工程位于 `G:\Rust\DeviceForge`，包含 backend 和 frontend；旧工程仅用于业务取证。crate 的 `apk-*` 包名保留以减少无关改动，产品名采用 DeviceForge。

## 后端文件骨架与依赖
`domain` 定义实体、端口和规则；`application` 管理操作注册、输入验证和任务生命周期；`infrastructure` 实现设备工具、受控进程、SQLite 与进程插件；`plugin-sdk` 是独立公开协议；`server` 负责 HTTP/MCP 和启动装配；`plugins` 放可单独发布的示例。每个模块有中文 README；测试置于对应 crate 的 tests 或单元模块。后端文档只存 backend/docs。

方向：server 调用 application；application 依赖 domain；infrastructure 实现 domain 端口并引用 plugin-sdk；plugin-sdk 禁止依赖宿主内部类型。具体适配器只在启动装配处注入。大型功能继续拆分 adapter/feature crate，禁止扩大万能工具类。

设备扩展方向已进一步明确为基础宿主加独立平台插件，见 [设备适配器插件架构](设备适配器插件架构.md)。上述当前平台装配待迁出；目标装配只注册通用提供者，不直接构造 Android/Harmony 等实现。平台工具、输入、安装和性能调用逐步迁入独立插件，保留任务、产物、日志和会话等宿主公共服务。

## 可读性与性能规则
先确定业务用例、输入和错误，再实现适配器。不得逐行翻译旧 IPC 或混杂页面逻辑。设备命令构造与输出解析分离；复杂规则用具名类型和函数；禁止用长分支实现全部设备平台。

注册时编译模式；任务并发和队列容量都有上限；输出与 HTTP 输入都受控；事件持久化且游标读取；超时、取消和服务退出必须收敛资源。当前 SQLite 仍是同步 Mutex 适配器，后续应引入有界数据库工作线程并测量锁等待和吞吐，不能宣称已经验证生产性能。

性能验收以真实负载为准：提交延迟、事件查询延迟、排队时间、并发工具进程数、内存与数据库增长。插件异常不得污染宿主终态；执行器 panic 转为任务失败，不能泄漏队列容量。

## 分阶段交付
阶段 1：文档、骨架、插件公开协议、任务层、HTTP 与 MCP、示例插件。阶段 2：产物服务、设备安装截图、APK 结构分析和受控配置。阶段 3：性能、Frida、自动化和投屏插件。阶段 4：工具供应及各业务行为真机验收。前端本轮只交付独立骨架与约束，完整界面另行实施。

所有阶段遵循迁移清单，以实现文件、失败路径测试及真机证据推进。当前的无设备测试只能证明协议与调度行为。
