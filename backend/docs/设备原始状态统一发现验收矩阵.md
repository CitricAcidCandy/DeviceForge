## C：受控存储与时钟七组

| 场景组 | 门闩或受控条件 | 直接观察与最少变体 |
| --- | --- | --- |
| C01 | Executor 记录调用；输入准入及 Job 创建前后计数 | 三入口各一次成功只一 Job/一调用；RAW-G01 每类坏输入零 Job/零调用、不清前次目录、不占额度 |
| C02 | 两个在途发现先 ready；第三项提交；其中一项进入未完成清理 | 额度覆盖不同入口；第三项按 F03 精确拒绝且无 Job 泄漏；清理未收敛前不能提前放行；收敛后许可恢复 |
| C03 | 同 provider 执行锁、工作槽和跨代等待分别占用；原准入时钟冻结 | refresh→direct、direct→alias、alias→refresh 三组合；等待 20 秒后目标只剩 10 秒，或等待到期零调用；等待时不清上一合法目录，真正执行才清 |
| C04 | 解析后、transition 前后和 publish 前设独立门闩；Store 返回实际旧终态/错误 | 取消/到期、存储失败、transition 已是 Cancelled、历史成功但拒绝发布分别按 F04/F05；不改终态，不重计时，候选对动作不可见 |
| C05 | 注册快照观察器、发布/卸载/重载和旧 finally 门闩 | 发布/撤销同 owner 的原/别名/provider 一致；旧代晚结果不能复活，旧失败不能清新目录。原子性看受控注册快照与决定点，不看 HTTP 两次采样 |
| C06 | A 已接受但等待者尚未取回，B 再发布；随后释放 A 等待者 | A 取得本 Job 的 A 回执或冻结的明确拒绝，不能读取最新 B 猜自己的结果；GET 为 B。等待者丢弃时工作继续受 tracker 跟踪，不积累无界回执缓存 |
| C07 | 非合作/合作清理、请求/Future 丢弃、cleanup_failed、shutdown 准入竞争 | 原任务到清理收敛才释放许可/串行锁；清理未确认拒绝新和排队，不由 Future 丢弃宣称完成；关闭后不能新增被漏跟踪的发现工作 |

时钟步骤遵循既有 BIND-004 经验：

1. 真实 SQLite/Node I/O 初始化先完成，再暂停；或者运行时从一开始暂停，但在真实 I/O 阶段显式恢复。等待 ready 用有界真实观察和持续 yield/mpsc 观测，避免无可运行任务触发 Tokio 自动推进。
2. 用 `tokio::time::Instant::from_std(context.deadline)` 比较执行端收到的原截止点，记录准入、开始执行及剩余预算；不拿暂停后偏移的 `std::Instant::now()` 当业务时钟，不重新启动相对 timeout。
3. 到期测试先断言数学原 deadline 已精确到达；Tokio 1.53.2 的毫秒粒度观察唤醒允许再显式推进 1 毫秒并断言观察时钟，不更改 context、总预算、过期零调用或 watchdog。跨 61 秒的真实动作存活观察不需要把这一刻度加到业务期限。
4. 独立墙钟上限只防测试失控；不参与生产期限或清理宽限，不因调度压力放大。恢复时钟后完成清理和直接 PID 观察，整个虚拟时钟过程保留门闩阶段证据。

C04/F04 未裁定前不自行引入提交状态或补偿机制。若选历史成功但目录可拒绝的方案，必须分别记录实际历史终态、发布回执和当前目录；若要求共同决定点，则新增存储失败/重启用例验证该机制后才能宣称一致。
