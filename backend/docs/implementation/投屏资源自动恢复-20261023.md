# 投屏资源自动核对与恢复

## 本轮范围与分工

模式为 architecture-first，以公开恢复契约和失败行为回归结合实施。插件只修改 `plugins/mirroring`，宿主、SDK、HTTP/MCP、前端及生成接口由其他协作者负责。运行库既有取消补帧保持原样。

选择持久资源台账加操作系统租约，而不是自动清除 `cleanup_failed` / `blocked`。入口、文件、远端规则、命令执行、恢复编排分别落在独立模块，避免将状态机、文件和 ADB 操作堆入一个入口。

详细职责、存储、顺序与安全限制见 [插件恢复模块](../../plugins/mirroring/src/recovery/README.md)，公开契约见 [插件资源恢复第一版](../contracts/插件资源恢复v1.md)。

## 契约接线

清单顶层声明 `recovery:{api_version:1,operation:"runtime.recover",timeout_ms:30000}`；该操作不进入普通业务贡献列表。普通协议4请求由 `lib.rs` 提前分流，直播仍为协议5。

输入必须是 JSON 对象，允许原会话直播参数；恢复只读取合法的 `device_id`。空对象扫描全部资源，指定设备也不缩小全插件扫描。输出使用 SDK `RecoveryReport`，显式包含 `coverage:"plugin"`、`inspected`、`remaining`，最多64检查项、每段不超过500字，不包含设备路径、执行命令或任意工具输出。

所有恢复资源类别都进行完整扫描，不按检查列表截断扫描。异常、文件损坏、超限或扫描未完成时返回阻断；`remaining` 至少为一项未确认的全量扫描义务，不能报告为零。只有完整扫描和复扫成功且剩余为零才允许宿主进一步根据真实协议终态解除风险。

## 持久身份和恢复门禁

- 入口从首帧前持共享进程租约，普通调用或直播即使还没有创建资源也阻止排他恢复。特殊恢复从入口识别操作后改取排他租约，持有至协议处理结束。
- 台账在首个 ADB 副作用前原子落盘，后续四类阶段前后更新。工具监督持有资源租约和进程共享租约；未确认退出时不能以等待 Future 结束释放归属。
- Windows 本机直接进程以 PID 加出生时刻识别，恢复检查旧直接子进程仍存活则忙碌。设备端以 token、目录、SCID、固定版本、PID、启动时刻及启动标识联合核对。
- 同设备恢复与资源登记互斥，整体手动恢复与全部普通插件调用互斥；控制状态更新在原协调锁及存活锁保护下原子发布，修订递增，不删除锁文件。
- 正常资源释放全部确认后撤销记录。崩溃记录保留到设备资源和关联控制状态均确认，不把目录缺失、父进程消失或转发删除回执单独当成恢复成功。

## 自动恢复与异常分类

新直播入口先核对目标旧台账及持久控制状态，再注册控制和创建本次资源。合法存活观看者不被自动清理。死去持有人的工具租约、无法证明的进程、归属冲突、损坏台账、无台账旧资源均阻止新资源创建。

自动核对未确认通过 `CleanupOutcome::Failed` 回传宿主，以便统一风险视图和恢复入口可见。单纯参数错误、未配置服务及正常恢复门禁忙碌不冒充资源清理故障。恢复不会重新发送业务输入，不重新执行录制或已经开始的创建动作。

无台账旧状态只允许对可定位设备做严格只读审计；发现无法归属的资源时明确拒绝。普通录制额外登记外部工具资源债务，避免全插件扫描遗漏非直播任务留下的远端资源。

## 释放与用户最新策略

旧失败终态不应阻止用户结束工作台。冻结05的release用例与HTTP/MCP共用：已结束记录不因Failed/Unconfirmed返回409，活动会话在真实监督结束后回收内存记录，原清理结论不重写。两种前端消费模型收到失败终态也退出本地占用，保留错误和日志；释放相关41项通过。

用户进一步要求旧调用隔离、后台强制回收、新调用直接分配新资源。该默认策略尚未完整实施，不能用本轮恢复按钮和释放窄修宣称已消除全局准入阻断。下一阶段以 [资源故障隔离与后台回收裁定](资源故障隔离与后台回收裁定.md) 为准。
