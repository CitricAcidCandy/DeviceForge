# 剩余包操作薄适配实施接缝

## 状态与目标

日期：2026-10-10，文档版本 v2。本文是 architecture-first 接缝设计，入口候选尚待主代理开放源码写集；文档版本不计入实现。以已冻结《包分析薄适配第一批裁定》及其补充为期限与工具观测依据；《包核心薄适配实施接缝》为旧接口取证，不以其中旧短限额建议覆盖新裁定。本批只读核对其余四项本地纯包操作：构建 APKS、反编译 APK、SDK 扫描、按规格提取分包。没有修改 Rust、执行命令、格式化、构建、测试或启动服务。

v2 修订明确：Some(D) 所有阶段直接共享同一个原 D，不用旧120秒限额截短；None 分别保持旧完整 work 或阶段上限。共享阻塞容量本批确定为4，各适配器 owner 状态分离。工具未确认使用持久标记，worker 未确认按真实闭包动态排空观测；不新增或宣称已实现服务 shutdown 确认。

目标是把 application 已确定的标准库绝对截止点 D 经默认兼容领域入口送到副本、工具、监测、同步核心与发布，真实替换重复解析/打包，并使取消、Future 丢弃后的实际工作状态可观测。本地调用不经过插件 Request，实施不必等待公开跨进程 D；独立插件上下文和部署加法继续另批，不能据此宣称七项独立插件迁出完成。

影响面为 domain 的三个包端口、application 的三个贡献模块、infrastructure 的工具包装/包 worker/四流适配与其测试、server 装配时的共享池注入。业务输入、输出 DTO、既有操作 ID、HTTP/MCP 模式保持原定义。`SplitPackages::install` 仅作为混合模块边界核对，不新增其 context 入口、不改设备连接、写锁或安装业务。

结构裁定：本批共享阻塞容量固定为4，把容量与每适配器 owner 状态分开，再显式注入四流；每适配器另建四槽池会让部署总量随适配器数增长，直接共享现有整份 Pool 又会混用未确认状态。保留一个受限阻塞容量来源和各端口自己的资源观测，不向纯核心引入 Tokio 或宿主端口，不借新池引入未实施的 shutdown 生命周期端口。

验证顺序采用 Hybrid：先用 Recorder 证明四条 context 和旧仅实现者兼容，再以坏包/文件/监测控制点证明规则及原 D，最后真实工具取消、Drop、共享容量与空宿主。完整门禁和真实运行均由主代理协调，本设计不借记首批通过结果。

## 现有四流与兼容入口候选

以下签名描述参数类型与顺序，方法均有 `&self`、async、返回领域 `Result<T>`。context 末参固定使用现有 `apk_domain::ExecutionContext`；它只传 `Option<std::time::Instant>`，领域不得导入核心、Tokio Instant 或进程实现。

| 当前精确端口与公开操作 | 候选 context 入口 | 默认兼容与应用接线 |
| --- | --- | --- |
| `BundleBuilder::build(request: BuildApksRequest, cancel: CancellationToken) -> Result<BuiltApks>`；`android.package.build_apks` | `build_with_context(request, cancel, context) -> Result<BuiltApks>` | 默认调用旧 `build(request, cancel)`。`BundleOperations` 预检后完成原反序列化与 `request.validate()`，调用新入口。 |
| `PackageReverse::decode(id: &str, cancel: CancellationToken) -> Result<DecodedPackage>`；`android.package.decode` | `decode_with_context(id, cancel, context) -> Result<DecodedPackage>` | 默认调用旧 `decode(id, cancel)`。`ReverseOperations` 保留产物 ID 提取与 DTO 序列化，原 D 直接转交。 |
| `PackageReverse::scan_sdks(id: &str, rules: Vec<SdkRule>, cancel: CancellationToken) -> Result<SdkScan>`；`android.package.scan_sdks` | `scan_sdks_with_context(id, rules, cancel, context) -> Result<SdkScan>` | 默认调用旧 `scan_sdks(id, rules, cancel)`。保留 rules 必填/反序列化与读 store 前规则校验；不以新增 context 绕过入口验证。 |
| `SplitPackages::extract(request: ExtractSplitsRequest, cancel: CancellationToken) -> Result<ExtractedSplits>`；`android.package.extract_splits` | `extract_with_context(request, cancel, context) -> Result<ExtractedSplits>` | 默认调用旧 `extract(request, cancel)`。`SplitOperations` 仅该分支改为新入口；`android.app.install_apks` 仍调用原 `install`。 |

三个领域 trait 各加候选 `fn has_unresolved_resources(&self) -> bool { false }`；三个对应 Executor 实时转发，不缓存为 false。领域默认法只保证旧实现源码兼容，它不会让旧工具/worker 自动获得全阶段 D。适配器覆盖新入口后，旧领域方法可以委托新入口的 default context，形成单条生产实现；不得默认法与覆盖法互相调用产生递归。

application 的候选 `execute_with_context` 使用既有 `operation_budget::check(context.deadline.map(tokio::time::Instant::from_std), Some(&cancel))`，预取消/预过期零端口调用；`execute` 委托 `ExecutionContext::default()`。检查成功后只做既有参数转换，送出的 context 仍是原对象，不重新计算 deadline。Unknown operation 的既有错误顺序需要回归锁定；到期与取消同现按既有 Timeout 诊断规则，不改变终态竞争。

`ReverseOperations` 两项共用同一 PackageReverse 实例，因此资源观测属于该适配器实际持有的 owner 集合；`SplitOperations` 同时暴露 extract/install，trait 级观测不能把接口存在当作 install 清理已完成的证据。新增追踪至少覆盖本批 extract 的实际资源，未改安装路径继续标记独立缺口。活跃但仍正常被等待的 worker 不应使任何操作被误判为清理失败。

## 四流实际阶段、模型与核心替换

所有路径在本节相对 `backend/crates/infrastructure/src/`。适配器只保留编排、宿主错误和模型映射，核心解析循环不再复制在旧模块。

| 流与当前落点 | 必须覆盖原 D 的阶段 | 保持的结果与规则 |
| --- | --- | --- |
| Bundle：`bundles/mod.rs::build_with_timeout`、`bundles/validation.rs::check` | request 校验 → 管理员工具/签名配置 → `.aab` 私有副本 → bundletool `build-apks` 与 100ms 输出监测 → 共享 worker APKS 校验 → 读取与发布 | `BuiltApks { source_artifact_id, mode, artifact, apk_count, universal_entry }`，`built.apks`。固定 `--max-threads=2`；核心 `Archive::open` 后 `validate_apks`，Default 可多 APK，Universal 唯一 `universal.apk`，外层 CRC/长度及压缩64 MiB、展开256 MiB。 |
| Reverse.decode：`reverse/mod.rs::decode`、`monitor_output`、`reverse/packing.rs` | `.apk` 私有副本 → apktool `decode` → 500ms 树监测 → 工具与监测都退出 → 共享 worker 最终 scan/pack → 发布 | `DecodedPackage { source_artifact_id, artifact, files, unpacked_size }`，`decoded.zip`。核心 TreeProfile::Reverse，含目录10000、深128、文件总量/ZIP各64 MiB；监测不要求完整必要成员，最终须唯一非空 apktool.yml/AndroidManifest.xml。 |
| Reverse.scan：`reverse/mod.rs::scan_sdks`、`reverse/scanning.rs` | 规则预检 → `.zip` 私有副本 → 共享 worker 全目录结构/去重、validate_decoded、scan_sdks → 原 D 完成复核 | `SdkScan { artifact_id, findings }`。规则1..100、唯一有界，smali/classesN 和包边界/指定类语义保留；每规则最多10条排序证据。无工具、无输出产物。 |
| Split.extract：`splits/mod.rs::extract_with_timeout`、`validate_source`、`monitor`、`splits/packing.rs` | request/spec 校验 → `.apks` 私有副本 → 共享 worker Default APKS 校验 → 本次 scratch 内 spec JSON 写入 → bundletool `extract-apks` 与100ms树监测 → 排空 → 最终 scan/pack → 发布 | `ExtractedSplits { source_artifact_id, device_spec, artifact, apk_entries }`，公开 `selected-apks.zip`，内部 `selected.zip`。核心 TreeProfile::Splits，含目录1000；监测早拒非 `.apk`，最终空/坏 APK 分证，不能借通用 scan 放宽旧资格。 |

关键兼容：通用核心 Structure 保留重复成员，旧宿主入口要对整个目录拒绝重名；不是只对选定条目检查。Reverse 工具最终缺必要文件映既有 Dependency，SDK 输入缺必要文件映 Invalid；Split 最终空映“工具没有生成匹配的 APK”，非 APK 映“提取目录只允许 APK 文件”；文件变化仍 Conflict。文本/XML/APKS/树/复制限额按既有场景区分，不能把通用结构旧 Invalid 超限全部统一改成 TooLarge。

首批签名/XML 错误映射和原 DTO 来源沿《包核心薄适配实施接缝》继续适用。独立插件的后续输出只声明 SDK outputs，真实宿主 Artifact 来自严格发布结果；本地直接 ArtifactStore 发布也不能跳过既有门禁。

## 原 D、cwd 与文件输出 until 接口

### 本地时钟转换与 None 兼容

Some(D) 仅执行 std → Tokio `Instant::from_std(D)`，传同步核心时用最初 std D 或原 Tokio点的 `into_std()`。准备、工具、监测 tick/工作池等待、最终打包、spec 写入和发布前后都直接复用 D。等到许可后与每次副作用前复核，不以新 `now + budget` 续时，不对Some(D)另叠旧120秒阶段上限。

已冻结裁定禁止工具阶段使用 `min(D, 工具启动点 + 120秒)` 截短Some(D)。一个原D即该次调用的统一业务截止点；旧120秒期限只用于None兼容。旧None的阶段行为需分别保持：

| 旧入口 None | 原时间语义基线 |
| --- | --- |
| Bundle.build | `build_with_timeout(..., TIMEOUT)` 将完整本地 work 限制120秒，内部工具亦120秒；不能替换为每阶段各得120秒后延长完整 work。 |
| Split.extract | `extract_with_timeout(..., TIMEOUT)` 完整 work 120秒，内部工具120秒；保留原 request 验证和工作边界。 |
| Reverse.decode | materialize、ToolCommand.output、最终打包等待、发布分别有旧120秒阶段限额；当前没有与 Bundle 相同的完整 work 120秒包围。不能因新增 context 把 None 强行改为完整120秒。 |
| Reverse.scan_sdks | materialize 与扫描 worker 等待沿旧120秒阶段；规则校验在读产物前完成。 |

None 在核心仍不自动补预算。调用方只在None分支确定一次既有完整work点或相应旧阶段点，并传给相关工具/worker；复核该点也不能宣称外层timeout已返回即后台工作停止。None 的阶段总量是否收敛为统一完整点须另批裁定，不能在兼容法中暗改；Some(D)绝不经过这个兼容分支。

### 候选 until 包装

以下接口仅为待裁定的本地 infrastructure 包装，参数顺序保持旧签名并将 timeout 替为 Tokio绝对点；不新增平台业务或 shell。旧 Duration 签名仍负责建立一次旧阶段点，再委托 until 版本。

```rust
// 在原 cwd 和受限环境中运行；返回 stdout，不重新获得阶段预算。
pub(crate) async fn run_isolated_until(
    executable: &str, args: &[String], deadline: tokio::time::Instant,
    cancel: CancellationToken, directory: &std::path::Path,
) -> apk_domain::Result<Vec<u8>>;

// 保留合并 stdout/stderr 且不 trim 的原诊断格式。
pub(crate) async fn isolated_text_until(
    executable: &str, args: &[String], deadline: tokio::time::Instant,
    cancel: CancellationToken, directory: &std::path::Path,
) -> apk_domain::Result<String>;

// 保持原环境规则及借用输出文件；Stdout 使用 limit，Stderr 独立限额。
pub(crate) async fn run_to_file_until(
    executable: &str, args: &[String], file: &mut tokio::fs::File,
    limit: u64, deadline: tokio::time::Instant, cancel: CancellationToken,
) -> apk_domain::Result<()>;
```

`process::run_until` 已接绝对点；首批部署命令移至 `package_tools/tool.rs`，`ToolCommand` 重导出保持原路径。其 `output_until` 在Some(D)直接使用原D，仅None采用120秒兼容期限。Bundle 沿 `run_isolated_until` 保持 cwd、Restricted 环境与 TEMP/TMP/TMPDIR 指向私有目录；Split.extract 沿 `isolated_text_until` 保留合并诊断及失败词判定。Reverse 现用 `ToolCommand.output`，没有显式 cwd 且继承普通工具环境；最小兼容替换为 `output_until`，不能悄然改成 restricted/cwd 模式。其 framework 已是本次私有路径；若后续统一 tool cwd/env，须单列兼容与真实工具门禁。

四流的 ZIP/APKS 不是标准输出流：Bundle/Split 由工具 argv 写输出路径，Reverse 由核心借用 std File 打包。`run_to_file_until` 是公共包装的完整期限接缝，不应为了使用它改写这四流的工具输出协议；无需制造标准输出业务分支。它须保留 FileIo→Storage、文件 Stdout 超限→TooLarge、Stderr 超限→Dependency、非零退出带退出码、CleanupFailed不丢失。

until 实现首次 poll 与 spawn/首次业务写/文件写前都优先检查取消与期限，不能仅用 `timeout_at(work)` 假定已过期 work 不会先被 poll。直接进程清理复用公共 tool-process 既有2秒上界；清理失败保持 CleanupFailed。等待真实退出与继续业务 I/O是不同资格，D到期后允许有界清理，不允许继续写新的包业务输出。

## 共享池、资源 owner 与监测排空

### 当前首批能力与需要推广的边界

首批 `package_tools/worker.rs::Pool` 已使用4槽 Semaphore；许可移进真实阻塞闭包，`Waiting` 丢弃时发取消并置 detached，`Finished` 在实际闭包退出时置 finished，`unresolved()` 只观察 detached 且未完成。日志使用 `LogContext::sync_scope` 与原 tracing span。该池目前是 `pub(super)`，slots 与 states 同属一份 Pool，不能直接从四流引用并假称跨模块共享已完成。

剩余流现有 `spawn_blocking` 虽持有 `Arc<Temporary>`，仍缺共享许可和 detached/finished 观测；包装外层 timeout 或丢弃 JoinHandle 不会停止真实闭包。本批把首批模式推广到 infrastructure 内部通用包工作模块，容量共享、owner状态分离，明确区分三种对象：

| 候选对象 | 输入、输出与责任 | 不承担的职责 |
| --- | --- | --- |
| 共享容量池 | 同一部署实例固定总4槽的包核心阻塞许可，七项包流与监测检查共用。等待以原 D/取消有界，取得后复核。 | 不把全局其他 owner 的活跃/未确认状态返回给某个具体端口；不限制 HTTP 并发或工具子进程总数，不承诺服务退出排空。 |
| 每适配器worker资源组 | 分别由 PackageAnalyzer、BundleBuilder、PackageReverse、Split.extract所属实例持有；登记本owner的detached/finished状态与lease。真实闭包持有许可至结束；仅detached且未finished表示worker未确认。 | 不把正常仍被等待的work当成清理失败；不读取其他owner状态，不清除工具持久标记，不宣称安装/设备资源已覆盖。 |
| 每适配器工具观测 | 对实际工具Future使用原D、取消树与Drop守卫。等待被丢弃或结果CleanupFailed后将本实例工具未确认标记持久置true，后续成功不能清零。 | 不以该标记声称直接进程、Java派生树、目录或shutdown已排空；普通并发工具与已确认的普通失败不置位，不自行引入新的后台shutdown端口。 |

worker资源组weak状态的创建、登记、清除及升级需在同一同步边界内完成，避免同一工作出现两份状态或“仍运行但观测列表已移除”。完成证据在实际文件句柄/permit/目录lease释放的顺序明确后写入，不能把外层等待结束作为finished。异常锁状态和无法确认清理按保守未确认处理。端口 `has_unresolved_resources` 合并本实例工具持久标记与worker动态状态；共享Semaphore不共享这两种owner观测。

一个共享池只限制同步核心工作，不能借它宣称工具进程、上传验证或全部宿主任务也总计4个。工具数量继续受应用既有任务准入限制；如要独立工具池需另裁定。池不可在一次长工具调用全过程持有阻塞许可，再让该任务的监测去申请同池许可，否则四个工具各占一槽可令监测/最终工作死等。工具异步运行不占核心 permit；一个扫描或打包闭包从启动到真实退出占一槽。

### 监测与工具的有序收口

候选监测只承担安全性和增量限额检查，不在工具仍写入时要求最终包完整。每个请求最多一个监测检查在飞，当前检查退出后才进入下次间隔；没有许可时用原 D/取消等待，不为每个 tick另排一个后台线程，也不在监测闭包内部递归申请同池许可。

1. 请求准入后创建operation子令牌及独立monitor子令牌；D保持原值。工具Future加本适配器工具观测守卫，monitor在飞检查登记到同owner的worker资源组。如监测实现确需Tokio spawn，使用 `LogContext::propagate`；同步worker继续用原日志scope。关联ID不从原业务input读取，不能将本实例登记冒称application已有shutdown追踪。
2. Bundle每100ms用异步 metadata检查 built.apks 普通文件/链接与64 MiB；Reverse每500ms共享worker扫描 TreeProfile::Reverse；Split每100ms共享worker扫描 TreeProfile::Splits并执行旧非APK早拒。NotFound表示尚未产出，不先报最终空/缺成员。
3. 监测失败、请求取消或D到期：先固定业务停止原因并取消operation令牌，再等待工具及在飞监测worker真实退出。监测错误不自动覆盖工具CleanupFailed；工具仍在清理时不删除scratch、进入最终扫描或发布。
4. 工具正常退出：只停止monitor子令牌，保持operation令牌；收回timer、等待在飞监测检查退出后才最终scan/pack。计划内monitor停止的Cancelled可归为该阶段正常停止，必须区分真实请求取消/原D到期/已有监测错误，不能把Timeout和CleanupFailed吞成成功。
5. 最终核心与发布前复核D/请求令牌；必要资格必须重新验证，不以最后一次监测成功替代最终结果。此时没有工具写者，但仍须保证私有副本内容稳定，tree快照不是不可变字节快照。

旧 `select` 的工具分支胜出会丢弃另一个monitor Future。若其已启动阻塞闭包，丢弃等待仍留后台检查；新的收口必须主动停止并等待实际工作，不因“成功退出路径”而漏掉状态/lease。不能用一个 child token同时表示正常monitor停止和取消整项业务，否则正常完成也会被判Cancelled。

### 工具持久标记与worker动态排空

请求Future的Drop守卫只发取消并更新观测，不做同步阻塞清理。worker等待被丢弃后标记detached，真实闭包仍持permit、文件和目录lease；实际退出置finished后，该项worker动态未确认可以解除。正常被await的worker不置detached。各适配器只观察本owner状态，不读取其他适配器正常执行中的任务。

工具Future与worker的完成证据不同：普通取消路径保持并await既有工具Future，从返回结果判断直接进程清理；若该Future已被丢弃，公共tool-process内部清理可能继续，但当前capture接口没有向包端口交出Drop后完成确认。此时工具标记持久true，不能等待worker结束或后来工具成功就恢复false；CleanupFailed同样置位。正常并发运行或已确认的普通失败不置位。这个持久标记是资格不足证据，不是清理实现或派生树排空证明。

本批不新增close/drain或shutdown确认端口，也不声称application的tracker自动追踪丢弃后的infra工作。资源守卫保证真实worker持有对象到退出，工具持久标记保留未确认资格；它们不证明服务退出已等待所有后台线程、Java派生树或目录重试。不得用runtime结束、未await的spawn、Semaphore关闭或unresolved暂时false推导整机shutdown已确认。需要更强退出生命周期时另批冻结端口、准入/登记与关闭顺序，不扩大本地四流实施。

业务到期/取消后的既有有界清理期不赠送业务预算。直接工具清理失败保留CleanupFailed；worker超时/丢弃不停止真实闭包，仍由闭包保留许可和目录，动态状态按实际退出更新。要求资源确认的边界必须合并工具与worker观测，不能只返回普通Timeout就称清理已完成。Job终态一旦确定不被晚结果改成功。当前本地包端口资源组不是动态插件的owner/generation：不能仅因has_unresolved转发就声称本地端口已具备插件卸载、同owner后续任务禁入或安全重载。若裁定统一这类准入，须明确与现有生命周期连接的独立写集，禁止清空资源组或owner更换绕过未确认工作。

`Temporary::drop` 的删除/Windows重试只是尽力释放目录，不能作为finished或cleanup确认。ArtifactStore.put的内部staging验证也可能在外层Future丢弃后继续；本批需说明发布等待与staging lease的真实归属及关闭顺序，不能只用外层 `execution_deadline::run` 就计完整排空。这里不承诺已提供跨产物事务、绝对物理文件快照或整棵派生进程树清理。

## 阻断错误与安装路径隔离

定点只读发现下列旧生产边界，已即时回流主代理；本轮不修改它们，下一批四流源码实施必须保留清理资格：

| 当前落点 | 具体风险 | 实施要求 |
| --- | --- | --- |
| `bundles/mod.rs` 构建工具结果的 `Err(_)` 固定诊断 | process返回CleanupFailed被改成Dependency。 | 固定脱敏只处理普通工具依赖诊断；Cancelled、Timeout、CleanupFailed原类别保留。 |
| `splits/mod.rs::tool_error` 只保Cancelled/Timeout | extract工具CleanupFailed同样被吞，且该helper也被install使用。 | 新extract_until路径明确保CleanupFailed；若修共用helper会影响install，必须由主代理另领相应写权并验证，不能借本批偷偷改安装行为。 |
| Bundle/Reverse/Split监测分支 `let _ = running.await` | 监测失败后工具有清理失败仍被忽略，可能只返回监测错误。 | 清理结果须参与最终资格；未确认时返回CleanupFailed且不发布，保留原监测错误作为有界非敏感诊断，不覆盖清理失败。 |
| Reverse等外层timeout/drop JoinHandle | 返回Timeout后实际worker可能继续，端口未观测。 | 许可、目录、join和detached/finished归资源所有者追踪；超时不等于后台停止。 |

`SplitPackages::install(request: InstallApksRequest, cancel) -> Result<ApksInstalled>`、设备写锁/ADB解析/`install-apks` argv不在四流实现写集。候选extract新建原D的工具与源验证薄入口，旧install使用的无context helper保持兼容，不把其120秒设备路径强行接入新纯包预算。

若共用 `validate_source` 改为核心，需要保留旧无context包装和install输入校验，涉及实际安装分支/工具错误的行为变化单独分配。新增trait级unresolved不等于给install补全owner与设备锁排空；后续迁到设备插件时须独立验证。文档可记录这些边界，不能用四项包验收关闭设备安装或平台迁出。

## 工具与签名配置的安全来源

本地四流可以继续消费管理员现有配置，不需新增公开SDK或HTTP字段。工具命令及固定前缀来源仍为装配，不由artifact业务输入选择；保留argv逐项传递，无shell字符串：

| 操作需要 | 已有部署来源与安全边界 |
| --- | --- |
| Bundle.build / Split.extract | `APK_BUNDLETOOL_JAR`，`APK_JAVA` 缺省java；bundletool配置缺失仅相关能力失败。工具路径在调用前确定，cwd是本次scratch，普通input不能传JAR或程序路径。 |
| Reverse.decode | `APK_APKTOOL_JAR`，同管理员Java来源；decoded/framework是宿主控制的本次路径。当前普通环境/cwd规则不在本批暗改；输出和诊断不能包含任意部署凭据。 |
| Reverse.scan_sdks | 不需要Java、APK工具或签名材料，仅宿主产物副本、规则、核心和worker。不得给它增加平台工具前置依赖。 |
| Bundle签名 | `APK_BUNDLE_KEYSTORE`、`APK_BUNDLE_KEY_ALIAS`、`APK_BUNDLE_STORE_PASSWORD_FILE`、`APK_BUNDLE_KEY_PASSWORD_FILE` 整组由管理员提供；旧绝对现有文件与alias≤100/无控制符校验保持。密码通过 `--ks-pass=file:` / `--key-pass=file:`，不读取进input或结果。 |

工具Prefix与签名argv本身含部署路径和alias，不能整份记录原命令、继承原请求日志或返回原stderr。固定脱敏不能吞Cancelled/Timeout/CleanupFailed；它是信息暴露控制，不改变资源资格。既有“现有绝对路径”校验不等于签名文件不可变或不含链接，后续若收紧此规则需要单独声明兼容差异，不在本文伪称已提供凭据快照。

空插件/未配置工具时宿主启动不主动调用Java或要求签名材料；缺项在相关操作调用时给确定错误。本地迁出不引入插件私有env/清单字段；独立插件的部署配置如何获得工具和签名材料仍待后续裁定，restricted环境不能被当作自动继承全部旧变量的渠道。

## 主代理最多三项待冻结选择

1. **四流context与资源观测**：采用本稿四个末参ExecutionContext默认入口、三个默认false方法，application原D预检/透传，明确Split只extract接context，install不改。原DTO/模式及None阶段语义保持。
2. **共享池接线接口**：容量总4与每适配器owner分离已确定，剩余准确构造/导出接缝由主代理冻结；worker动态排空与工具未确认持久标记各自实现。无新增shutdown确认，Java派生树与发布staging的观测边界继续明确保留。
3. **until与错误资格**：冻结本地cwd/text/file-output绝对点包装，Some(D)直接同D、None旧期限兼容，保留环境/trim/错误文案；CleanupFailed原类、监测工具排空结果优先及零发布属于强制验收，不接受脱敏吞错。跨进程期限与插件部署协议不阻塞本地实施。
