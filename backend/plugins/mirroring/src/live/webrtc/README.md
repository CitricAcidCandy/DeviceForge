# WebRTC 投屏会话模块

`mod.rs` 负责一次协商、视频与控制编排、原业务期限及设备和连接清理。首期 WebRTC 固定关闭设备音频，兼容模式的音频合同不受影响。会话只协商一次，连接失败后由调用方重新打开，不重放控制。

`signaling.rs` 负责协议 1 的有界 JSON 行、answer 顺序和控制命令校验。协议 5 的宿主输入输出仅传信令和兼容控制；H264 与 Opus 媒体由 WebRTC 轨道发送。

`media.rs` 验证 scrcpy 的 H264、Opus 包头与配置，并按设备时间戳计算样本间隔。`reader.rs` 持有每条设备套接字和部分包读取进度；异步读取在协商或媒体选择分支被取消后，可从同一字节位置继续。协商等待时持续排空媒体，连接后请求设备重置视频并等待关键帧，复用已验证配置并校验后续新配置。

`peer.rs` 创建 ICE、DTLS、SRTP 连接、媒体轨道与有序可靠的 `deviceforge.control` DataChannel，并接收 RTCP。控制队列满或非法输入使会话失败；PLI/FIR 限频驱动设备重置视频。用户控制准入与内部视频重置分开。连接关闭和设备清理必须分别确认；任何未确认结果均向宿主报告清理失败。

`cleanup.rs` 只根据已完成的收尾结果生成失败说明，列出先前阶段、WebRTC连接、视频设备资源和设备控制端中的失败项，同时保留触发清理的原始业务错误。它不重试业务、不清除宿主故障标记，也不把后续成功当作先前未确认资源已经释放的证据。
